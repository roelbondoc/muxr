# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`muxr` is a keyboard-driven terminal multiplexer written in pure Ruby — Screen-style keybindings, xmonad-style automatic tiling, and a Quake-style drawer overlay. It is a **standalone Ruby gem**, not a Rails app. Unlike the other projects in this workspace, **muxr does not use Docker** — run Ruby commands directly. Like `slimmetry-ruby`, it follows the gem exception in the workspace CLAUDE.md.

Runtime depends only on Ruby ≥ 3.4 stdlib (`PTY`, `IO.console`, `JSON`, `FileUtils`). Dev-only gems: `minitest`, `rake`.

## Commands

```bash
# Run the multiplexer (bin/muxr puts lib/ on $LOAD_PATH itself, no -I needed)
bin/muxr                          # start the "default" session
bin/muxr work                     # start (or restore) a named session

# Tests — no Rakefile dependency needed for the file-loader form
rake test                                                              # full suite
ruby -Ilib -Itest test/test_layout_manager.rb                          # single file
ruby -Ilib -Itest test/test_terminal.rb -n test_csi_cursor_position    # single test
```

There is no lint config, no CI, and no build step (no bundler/asset/transpile).

## Architecture (the parts you have to read multiple files to see)

muxr runs as **two processes** talking over a Unix domain socket at `~/.muxr/sockets/<name>.sock`. PTYs and Session state live in the long-running server; the client is a thin TTY front-end that comes and goes during detach/reattach.

```
Client (foreground, owns the TTY)              Server (daemon, owns the PTYs)
 ├─ STDIN raw + alt screen                      Application (event loop, lifecycle)
 ├─ SIGWINCH → RESIZE frame                      ├─ Session (Window + Drawer + dimensions)
 │                                               │   ├─ Window  – panes[], focused_index, ...
 └─ Protocol                                     │   ├─ Pane[]  – Terminal + PTYProcess
     ◄── OUTPUT bytes ──── Renderer ◄────────────┤   └─ Drawer  – persistent PTY, toggleable
     ──── INPUT bytes ───► InputHandler          ├─ Renderer        – frame composer, diff-emits ANSI
     ──── HELLO/RESIZE ──► apply_size            ├─ InputHandler    – Ctrl-a state machine
     ◄── BYE ───────────── disconnect_client     ├─ CommandDispatcher
                                                 ├─ LayoutManager   – pure functions
                                                 └─ UNIXServer listener (accepts one client)
```

A few things that are not obvious until you've debugged them:

- **Two processes.** `bin/muxr <name>` always runs as the *client*. If no socket exists at `~/.muxr/sockets/<name>.sock` (or the existing one is stale), bin/muxr fork-execs itself with `--server <name>`, polls up to 3s for the socket to appear, then connects. Server logs go to `~/.muxr/logs/<name>.log`. Only one client may attach at a time — newcomers get a `BYE busy`.

- **Detach vs. quit.** `Ctrl-a d` closes the client socket but leaves the server (and all its PTYs) running. `Ctrl-a q` and `:quit` both flash `kill session? (y/n)` in the status bar and only tear the server down on `y`. There is no "kill without confirm" keybinding by design.

- **Protocol framing (`lib/muxr/protocol.rb`).** Every message is `[1-byte type][4-byte BE length][payload]`. Types: `H` hello, `I` input, `R` resize, `B` bye, `O` output. The HELLO and RESIZE payloads are `"ROWS COLS"` ASCII; INPUT/OUTPUT carry raw terminal bytes; BYE carries an optional reason string. HELLO can carry trailing `key=val` capability tokens from the width probe (e.g. `"48 200 ambiguous=2 glyphs=23fa:2,273b:1"`); `decode_size` reads only the first two integers so the size still parses, and `decode_caps` pulls the rest.

- **`FramedOutput` (nested in `Application`)** is the Renderer's `out:` sink. It packages each Renderer `write` as one `OUTPUT` frame on the attached client. When no client is attached, render is skipped entirely — PTY data still gets drained so Terminal grids stay current, and the first frame after re-attach is forced to be a full repaint via `Renderer#reset_frame!`.

- **Event loop is single-threaded `IO.select`** over the listening socket, the attached client socket (when present), every pane PTY, and the drawer PTY (when present). All PTY reads feed into the destination pane's `Terminal#feed`. The only off-main-thread work is `Application#start_foreground_poller`, which polls each pane's foreground command every `FOREGROUND_POLL_INTERVAL` (~750ms) and writes the result back to `pane.foreground_command`. Atomic pointer writes under the GVL mean the renderer's per-frame read needs no lock.

- **`Terminal` is a real VT100 emulator**, not a line buffer. It maintains a `rows × cols` grid of `Cell` (char + fg + bg + attrs) plus cursor and scroll region. It handles CSI cursor movement, SGR (16-color, 256-color, truecolor), erase/insert/delete, autowrap, and scroll regions. UTF-8 bytes are buffered across PTY read boundaries via `@feed_remainder`, but **only a genuinely truncated tail** (≤3 bytes, per `incomplete_tail_length`) is ever held back — any other malformed byte is scrubbed to U+FFFD. Deferring it instead would prepend the same bad byte to every later feed, so the stream could never become valid: one stray byte used to wedge a pane permanently and grow `@feed_remainder` without bound.

- **`Terminal` does NOT translate `\n` → `\r\n`** (line-discipline ONLCR is the kernel's job in a real PTY). When writing tests that feed multi-line input directly, use `\r\n`. This is a real footgun that bit the initial test suite.

- **Resizing a pane smaller pushes the lost top rows into scrollback** (`Terminal#resize` → `push_scrollback`, shared with `scroll_up_region`), because those lines scrolled out of view exactly as if the program had emitted newlines — dropping them silently left a hole in history you'd notice only after scrolling back. Relatedly, `\e8`/`\e[u` (restore cursor) **clamp** to the current bounds: `@saved_cursor` can outlive a shrink, and an unclamped restore indexed past `@buffer` and raised `NoMethodError` on the next printable byte.

- **A full-screen program gets its own grid (DECSET 47 / 1047 / 1049).** `Terminal` keeps the primary screen — grid, cursor, DECSC slot, scroll region and pen — in `@saved_primary` while an alternate screen is up, and `alt_screen?` is just "is that non-nil". Two things follow, and both are the reason it exists: `scroll_up_region` consults `history_scrolls?` so **nothing on the alternate screen reaches scrollback**, and `set_view_offset` pins the view to the live screen so you cannot page into a pager's frames. Without this a pager drew straight onto the primary grid and every page-down shovelled a screenful into history — 20 page-downs of `less` measured **+232 junk rows**, evicting that much real output at the `scrollback_max` cap — and quitting left the program's last frame smeared on screen instead of uncovering the shell. (`vim` escaped the history half of that by accident: it sets a partial DECSTBM region, which the `history_scrolls?` guard already excluded. It did not escape the smear.) Three consequences worth knowing. (1) **`resize` reshapes both grids** via `refit`, and only the primary's dropped rows are history — a pager's are not, so `refit` takes `history:`. (2) **`dump_ansi` leads with `primary_repaint`** when an alternate screen is up: the covered grid's repaint, then `\e[?1049h`, then the alternate grid. A mirror or a moved pane therefore holds *both* screens, so quitting the pager on the far side uncovers the same shell it uncovers here rather than a blank. The round-trip contract in `test_terminal_snapshot.rb` covers this. (3) `detect_urls!` stops splicing the last history row onto row 0, since that row belongs to the other screen. `#leave_stale_scrollback` drops the mode if a pane enters an alternate screen under a user already scrolling muxr's ring. Note `Renderer#enter_alt_screen` is a different thing entirely — that is muxr's own outer terminal.

- **`C-a [` drives one of two scrollers, and `alt_screen?` is not how it chooses.** The question is "will this program understand a wheel report?", and the program answers it itself by turning on DECSET 1000/1002/1003 — so `Terminal#mouse_tracking?` is the trigger and `alt_screen?` is only the fallback tier. This matters because **Claude Code is not a full-screen app**: it repaints inline on the primary grid (its transcript survives in your terminal's scrollback after it quits, which an alternate-screen app cannot do), so `alt_screen?` is false there while mouse tracking is true. Keying off the alternate screen would miss it entirely, and keying off `ForegroundCommand` — the other thing muxr knows — is worse still: it lags 750ms behind on a `ps` poll, needs a hand-maintained allowlist, returns nil for shells by design, and is structurally blind to mirrors, since `RemotePane#pid` is nil and `poll_foreground_commands` skips it. Mouse-mode tracking costs nothing on a mirror because the relayed byte stream carries the `\e[?1000h`. Three tiers in `Application#scroll_app`: mouse tracking → synthesised wheel reports at the pane centre (`MouseReport`, SGR when the program asked for 1006, X10 otherwise); else alternate screen → arrow keys, which is alternate-scroll emulation and the only reason `less` responds; else muxr's own ring. `Terminal#dump_modes` carries the mouse modes and DECCKM so a mirrored or moved pane picks the right tier. `#leave_stale_scrollback` demotes `:app` → `:ring` when the program drops mouse tracking — otherwise the wheel reports would land at a bare shell prompt as literal `[<64;41;13M`.

- **Selection is clamped to the live screen while the app is being scrolled.** A self-scrolling program repaints its viewport in place rather than emitting new lines, so **nothing it scrolls past reaches muxr's ring** — the ring's tail is whatever was on screen *before* the app scrolled and no longer continues into row 0. `Terminal#selection_floor` raises the timeline clamp to `@scrollback.size` under `confine_selection_to_screen!`, which `Application#enter_selection` sets from the scroll source. Without it a selection dragged past the top of the screen splices two unrelated regions into the paste buffer — silently, since both halves are real text. Same hazard as the `detect_urls!` row-0 splice above, same fix. `g`/`G` and `/` search stay on the ring for the same reason: only the program knows where its own history starts.

- **Scrollback depth is `Terminal.scrollback_max`, set once from `MUXR_SCROLLBACK`** (default `SCROLLBACK_DEFAULT` = 50,000, clamped to `SCROLLBACK_BOUNDS`). It is not a constant because the cost is real and per-pane, but it is no longer dominated by object overhead: **a history row is stored packed** (`lib/muxr/history_row.rb`) as one `String` of the row's characters plus a flat run-length array of `[len, fg, bg, attrs, hyperlink]`, and materializes `Cell`s only when a reader asks. A row with no styling at all keeps `nil` runs; a per-cell character-count array appears only when some cell isn't exactly one codepoint (a wide glyph's continuation half is 0, a base + combining mark is 2+); a blank row is the shared frozen `HistoryRow::EMPTY`. It used to be one `Cell` Struct per character, which is what made depth expensive — ~76 bytes and one live object per column. Measured on a corpus of real terminal output (coloured `git log -p`, a coloured diff, a test run) replayed at 160 columns until the ring filled, a 20,000-row ring went from 2.88 M live objects / +328 MB RSS to 0.07 M / +12 MB (26x, ~615 bytes per row against ~16 KB), and the retained profile is now `String` + `Array` rather than 216 MB of `Cell`. Three older wins still stand: `#pack_row` cuts each row at `#last_significant_column` so cost tracks content rather than pane width, `BLANK_CHAR` is shared, and `Terminal.intern_char` hands out frozen singletons from `ASCII_CHARS` so a million cells of text share 128 strings (it is a class method because `HistoryRow` materializes through it too). All of it relies on nothing ever mutating `Cell#char` in place — `#attach_combining` reassigns with `+=`, and `BLANK_CHAR`/`ASCII_CHARS` are frozen so a future `<<` fails loudly instead of corrupting every blank cell in the process.

- **A packed row materializes `Cell`s on demand, and they are cached rather than kept.** `HistoryRow` quacks like the `Array` of `Cell`s the readers expect (`#[]`, `#length`, `#each`, `#map`, `#empty?`), so `#visible_cell`, `#extract_selection_text`, `#collect_matches`, `#first_non_blank_col`, `#char_class_at`, `#last_significant_column` and `#emit_row` read a packed row with no changes; `#[]` past the content width returns `nil`, which is what lets `#visible_cell` fall back to a blank in one call. The first read builds the whole row's cells at once and parks them in a **process-wide cache of `HistoryRow::CACHE_LIMIT` (256) rows**, evicting the oldest through `#release!`. Materializing per call instead would churn more garbage per second than packing saves: `Renderer#copy_terminal` reads every cell of every pane every frame, and while the user is scrolled back most of those reads land in history. Measured over 100 frames of a 50×160 screenful read out of history, a static view allocates exactly what it did before (4,077 objects/frame — all of it `#visible_cell`'s blank-cell fallback, which is now the biggest allocator on that path), scrolling one row per frame is +2%, and holding page-down (50 fresh rows every frame, the worst case) costs +2,475 transient objects/frame against 16 KB per row retained forever. Walks that touch the whole timeline pay once: search over a filled 10,000-row ring 313 → 376 ms, `#dump_transfer` 191 → 285 ms.

- **A history row takes writes, and a write has to be repacked before the cache can drop it.** `#detect_urls!` splices `@scrollback.last` onto the live rows so a URL that wrapped across the top of the screen still reads as one click target, and it *mutates* those cells — clearing a stale `SYNTH_URL_PREFIX` link, stamping the new payload — so it calls `row.repack!` at the end of every scan. Until then the materialized cells are the row's only copy of that edit and `#release!` would throw it away. A future writer must do the same, and must not materialize a second history row in between: the eviction it triggers could be the row it is holding.

- **`#pack_row` keeps a trailing wide glyph's continuation cell** (`#wide_lead?`), even though `#last_significant_column` calls an unstyled continuation insignificant. Trim it and `#visible_cell` hands back a blank for that column, `#copy_terminal` puts a space in the frame where `""` belongs, and the `next if cell.char.empty?` guard in the Renderer's diff-emit — the thing that stops it painting over the right half of a wide glyph — never fires. The glyph gets a space stamped through it. Caught by `test_wide_glyphs_survive_interning_and_trimming`.

- **Every reader of a history row must tolerate a short row.** `#pack_row` means `row.length` is the content width, not `@cols`. `#visible_cell` falls back to a blank when `row[c]` is `nil`, `#first_non_blank_col` and `#char_class_at` use `row[c]&.char`, `#extract_selection_text` clamps to `row.length - 1`, `#collect_matches` substitutes `" "` for a missing cell, and `#emit_row` is only ever called with a `last` from `#last_significant_column`. A new reader that assumes `@cols` cells will read `nil` on the trailing columns of most history rows.

- **`HistoryRow` has two no-materialize fast paths, and their contract is that they agree exactly with the `Cell`-based ones.** `#search_text` (for `#collect_matches`) and `#to_ansi` (for `#row_ansi`) read the packed `String` and runs directly, never allocating a `Cell`. That is what made a 50,000-row default affordable: a full-timeline search of a filled ring went from ~1.3 s to **44 ms**. Three details carry it. (1) `#search_text` returns `[line, col_at]` where **`col_at` nil means the identity mapping** — true for any row without wide or combining glyphs, i.e. almost all of them — which skips allocating a `@cols`-sized map per row; `#collect_matches` must honour the nil. (2) `#to_ansi` computes `Terminal.sgr_for` **once per run, not per cell**. Style only changes at run boundaries, and computing it per cell (which is what `#emit_row` does, fine for the 50-row live grid) is what made `#dump_transfer` slow: per-run took it from 292 ms to 168 ms on a 10,000-row ring. (3) `Terminal.sgr_for(fg, bg, attrs)` was split out of `Terminal.sgr(cell)` precisely so a packed row can describe a cell it never built. The equivalence is pinned by `test_to_ansi_agrees_with_the_materializing_emitter` and `test_search_text_agrees_with_the_materializing_walk`, which run both implementations over a list of deliberately nasty rows — wide glyphs, coloured wide glyphs, stacked combining marks, box drawing, hyperlinks, a background run to end-of-line, trailing spaces. If you add a third fast path, pin it the same way; these are optimizations, so a divergence is a silent wrong answer rather than a crash.

- **Wide / combining characters use a continuation-cell convention.** `Terminal.char_width(cp)` returns 0 (combining marks, variation selectors, zero-width formatters), 2 (East Asian wide + emoji), or 1 (everything else); the ASCII/Latin-1 fast path short-circuits at `cp < 0x300`. A width-2 glyph is stored in its **lead cell** with a **continuation cell whose `char` is `""`** immediately to its right reserving the second column; a width-0 mark is folded onto the preceding cell's `char` (so `"e" + ◌́` becomes one cell holding `"é"`). This invariant is load-bearing across four readers: the `Renderer` skips `""` cells when emitting (the lead already spans both columns) and advances its emit cursor by `char_width`, not codepoint count; `dump_text` and `extract_selection_text` treat `""` as a no-op join; and `collect_matches`/`detect_urls!` build a codepoint→column (or →cell) map because the old 1:1 char-index↔column assumption no longer holds on rows containing wide/combining glyphs. If you add a fifth consumer that walks the grid, honor the same convention. Known gap: a resize that splits a wide pair, or DCH/ICH/ECH landing between the halves, can orphan a lead — cosmetic, self-heals on the next program redraw (or `r` / `Ctrl-a r` refresh).

- **`Renderer` forces an absolute cursor move after width-ambiguous glyphs.** The diff-emit only writes `\e[y;xH` when a cell isn't contiguous with the previously-emitted one (tracked via `last_x`/`last_y`). That contiguity shortcut is only sound when the outer terminal advances its cursor exactly as far as we predict. For East Asian Ambiguous symbols (`·`, `…`, `●`, arrows, the `⏺`/`✻`/`❯` glyphs Claude Code's UI is full of), CJK, and emoji, the outer terminal may draw 1 *or* 2 columns and we can't know which — so `Renderer#contiguous_after?` returns false for anything non-ASCII except the box-drawing/block band `0x2500–0x259F` *when the probe measured that band as narrow* (`Terminal.box_wide` false — see the width probe below), forcing a fresh CUP for the next cell. Without this, one width disagreement cascades and shifts the entire rest of the line (the classic "text doesn't line up, but resizing fixes it" bug — resize only *appeared* to fix it because the SIGWINCH made the inner program clear-with-spaces and repaint). Verified against `pyte` as a reference emulator: muxr's grid is byte-identical for steady-state and scrolling, and the incremental diff-emit produces the same outer display as a full re-render. A second, related guard: after emitting a glyph muxr models as **one** column but whose real width is uncertain (`Terminal.char_width == 1` but not contiguous-safe), the diff also **force-repaints the next cell even if unchanged** — otherwise an in-place animation (Claude Code's spinner) lets a 2-wide draw's phantom second half sit on the skipped neighbour until a manual refresh.

- **Inner cursor visibility is honored (DECTCEM, DEC private mode 25).** `Terminal` tracks `\e[?25h`/`\e[?25l` in `@cursor_visible` (alongside 2026/2004 in the same `?`-prefixed branch). `Renderer#cursor_position` returns a bare `\e[?25l` for the focused pane when its inner program has hidden the cursor, instead of painting muxr's block at the inner cursor's last write position. This matters for Claude Code and other Ink UIs: they hide the cursor for the whole render and only show it at a text-input prompt, so without this a phantom block smears across the animating progress line. (The command/search/selection prompt cursors are handled earlier in `cursor_position` and are unaffected.)

- **Notification passthrough (bell + OSC 9 / OSC 777).** These aren't grid state — they're things the inner program emits to get the *user's* attention, and a multiplexer that swallows them silently breaks "Claude finished in a background pane." `Terminal` collects them into `@pending_notifications` (a bare BEL in ground state; an `\e]9;…` or `\e]777;…` OSC, re-wrapped with a BEL terminator since the parser consumed the original ST). `Application#consume_pane_io` drains every pane's (and the drawer's) queue via `forward_notifications` and ships the bytes to the outer terminal as their own `OUTPUT` frame — out of band from the rendered frame, so a *non-focused* pane still rings/notifies. Bell/OSC don't move the cursor or touch the screen, so interleaving them between render frames is safe. When detached the queue is still drained (and dropped) and is capped at `NOTIFY_MAX` so a never-attached session can't grow it without bound. Window-title OSC 0/1/2 and palette OSC 4 are still silently consumed — propagating a background pane's title would fight muxr's own status bar; left as a deliberate non-goal.

- **Clipboard passthrough (OSC 52).** When an inner program asks to set the system clipboard (`\e]52;<targets>;<base64>` — what a vim yank with OSC 52 enabled, tmux, or Ghostty emit), `Terminal#finalize_clipboard` base64-decodes the payload and stashes it in `@pending_clipboard` (last-write-wins — a clipboard holds one value, so this can't grow unbounded; the encoded payload is bounded by `OSC_MAX_LEN`, which is why that cap was raised to 100 KiB and now doubles as the practical max yank size). `Application#consume_pane_io` drains it via `forward_clipboard`, which pipes it to `pbcopy` (reusing `spawn_pbcopy`) and mirrors it into `@paste_buffer` so `Ctrl-a p` pastes the same text — exactly like copy-mode's yank. Two deliberate departures from notification passthrough: it's drained **even when detached** (pbcopy is local to the server host, no client needed, so a *background* pane's yank still reaches the clipboard), and a base64 of `?` (a clipboard *query*) or an empty body (a *clear*) is dropped — muxr can't safely read the host clipboard back, and silently wiping it on an inner program's whim would be surprising.

- **Graphics land on disk, not on the grid (APC / kitty protocol).** muxr composites a cell grid and re-emits it every frame, so it has nowhere to put pixels — and the placement/clip/redraw bookkeeping real image support needs is a much bigger project. Instead `Terminal#finalize_apc` decodes the kitty transmission, `ImageStore` writes it to `~/.muxr/images`, and the pane gets one line — `[image 640×480 → ~/.muxr/images/….png]` — stamped with an OSC 8 `file://` hyperlink so Cmd-click opens it. Three things are load-bearing. **Chunking:** a transmission longer than ~4 KiB arrives as several APCs where only the *first* carries the control keys and the rest carry just `m=`; `@graphics_pending` accumulates the base64 text (concatenating encoded chunks is safe, they split on 4-char boundaries) and only saves on `m=0`. **Format:** `f=100` is already a PNG, but `f=24`/`f=32` are bare pixels that nothing on the host can open, so `ImageStore.encode_png` wraps them in a minimal PNG container (`Zlib::Deflate` + CRC'd IHDR/IDAT/IEND). **Queries:** `a=q` is answered `\e_Gi=<id>;OK\e\\` via `@pending_replies` — claiming support is what makes tools choose the kitty path over sixel, which we can't decode at all. The announcement re-uses `@current_hyperlink` (saved/restored around the write) rather than adding a second link mechanism, and its `8;id=muxr-img-` prefix is deliberately distinct from `SYNTH_URL_PREFIX` so `detect_urls!` neither strips it nor overwrites it — a wrapped path stays one click target.

- **APC and DCS used to corrupt the grid.** Before the above, `escape_char` had no state for `ESC _` (APC) or `ESC P` (DCS): the introducer hit the `else` branch, reset to `:ground`, and the entire body was `put_char`ed as text — a single plot dumped kilobytes of base64 across the pane. DCS/SOS/PM now share a `:string_discard` state that eats bytes to ST. If you add a new string-sequence introducer, give it a state; silently returning to `:ground` is never the right default.

- **Width probe (`lib/muxr/width_probe.rb`).** The deeper fix for width disagreement: instead of guessing, *measure*. On attach the client (it owns the TTY) prints test glyphs and reads the cursor column back via DSR-CPR (`\e[6n` → `\e[r;cR`); the column delta is each glyph's real display width. It votes on the East Asian Ambiguous class (→ `Terminal.ambiguous_wide`, covering the long tail in `Terminal::AMBIGUOUS_RANGES`), separately votes on the box-drawing/block band `0x2500–0x259F` (→ `Terminal.box_wide`, `Terminal::BOX_RANGES`), and records exact per-codepoint widths for emoji-presentation glyphs no class predicts — `⏺`/`✻`/`❯` (→ `Terminal.width_overrides`, which win over every heuristic). The verdict rides to the server in HELLO and `Application#apply_caps` installs it process-wide (the server hosts one outer terminal at a time). Falls back to defaults when the terminal doesn't answer CPR (timeout) or STDIN/STDOUT isn't a TTY. The box band needs its own vote rather than riding on `ambiguous_wide`: much of it is formally Ambiguous, yet many terminals special-case it narrow anyway — and it's the one band `contiguous_after?` trusts, so a wrong guess there shifts every later cell on the line. That band is what TUI borders are built from, and Claude Code's UI is mostly borders. The probe is why HELLO moved from `Client#connect` into `Client#run` — it needs raw mode first.

- **`Renderer#copy_terminal` clips to the pane's box, not just to the frame.** For a local pane the grid is always exactly the inner size, so this never mattered; a mirror's grid is sized by another session and can be a row or column out of step, and overrunning eats the border.

- **`Renderer` diff-emits cells.** It compares the new frame against `@prev` and only emits `\e[y;xH<sgr><char>` for cells that changed. Consequence: searching the raw output stream for a contiguous string like `"layout:grid"` will FAIL when only the differing glyphs changed position (e.g. `tall → grid` emits just `grid` at the position where `tall` was). Use targeted character checks or compose chunks before searching.

- **A borrowed pane is a mirror, not a move (`lib/muxr/remote_pane.rb`).** `A` / `C-a A` / `:attach` opens a picker (`PanePicker` + `SessionDirectory`, which asks every live `<name>.ctrl.sock` for its `panes.list`) and mounts the chosen pane here while it keeps running in its own session. `RemotePane` duck-types `PTYProcess` — `io` is the control socket, `read_nonblock` demuxes NDJSON and returns raw bytes — so the borrowed pane joins the event loop, the layout and the Renderer with no special-casing. **The owner keeps the PTY and stays its only reader**; that single-reader rule is what makes the whole thing coherent, and three consequences fall out of it. (1) **Geometry belongs to the owner.** The relayed stream carries absolute cursor addresses, so `Pane#resize` is a no-op on a mirror — it forwards the viewport it can offer (`pane.mirror_resize`) and the owner runs the PTY at the min across all viewers (`Pane#mirror_size`, `#fit_to_mirrors`), echoing the size back with a full `Terminal#dump_ansi` repaint. `#clamp_to_mirrors!` applies the shrink immediately because the owner may be *detached*, in which case no render — and therefore no `Pane#resize` — is ever coming. (2) **The replica must not answer DSR/CPR**; the owner already did, and a second reply reaches the inner program as keystrokes (`Pane#read_from_pty` skips `take_pending_replies!` when `mirror?`). (3) **Lifecycle is failure-shaped, not negotiated.** Owner stops → socket EOF → `alive?` false → `prune_dead_panes` drops it. Borrower stops (or `x`, or teardown) → `pane.unmirror` → the constraint clears and the pane carries on at home. A pane that disappears at the owner is announced by `event.pane.gone` from `push_mirror_geometry`, which is on the tick path and so catches every removal route without a hook per route. Mirrors are excluded from `Session#serialize` (`own_panes`) — restoring one would cold-start a second shell in someone else's cwd.

- **A move is an fd handoff, not a re-spawn (`lib/muxr/pane_transfer.rb`).** `m` in the picker sends the master pty fd itself over the control socket with `SCM_RIGHTS` (`UNIXSocket#send_io` / `#recv_io`), so the same shell process keeps running and just changes owner. **Wire order is load-bearing and counter-intuitive: preamble, then fd, then state.** The fd must precede the bulky emulator state because taking it out needs `recvmsg` — any plain buffered read that swallows its carrier byte first silently drops the fd; that's why `PaneTransfer.await_preamble` reads a byte at a time and everything after the `recv_io` can buffer freely. The preamble comes first because a refusal has no fd to send and the receiver would otherwise block waiting for one. **Two-phase commit:** `begin_handoff` marks the pane `handing_off?` (which drops its fd out of `Application#loop_forever`'s select sets — two servers reading one master would split the byte stream) but tears nothing down; only `pane.move_commit` calls `PTYProcess#relinquish!`. Anything short of that — receiver crash, client disconnect, `HANDOFF_TIMEOUT` — resumes the pane. `relinquish!` sets `@exited` before closing the fds, so the later `Pane#close` from `remove_pane` can't signal a shell that now has a different owner, and `Process.detach` keeps the (still-our-child) process from becoming a zombie. On the receiving side `PTYProcess.new(adopt_io:, adopt_pid:)` wraps the fd instead of spawning; the pid is not our child, so `waitpid` gives ECHILD (already rescued in `reap`) while `kill` and `ForegroundCommand.lookup` work fine. Two refusals exist for real reasons: the **last** pane can't be moved (`panes.empty?` shuts the server down, so it would end the source session as a side effect — the guard subtracts in-flight handoffs so two concurrent moves can't do it either), and a pane that is itself a mirror can't be moved on (its `io` is a control socket, not a pty; adopting it would feed NDJSON to an emulator). One thing the handoff deliberately cannot fix: the moved shell keeps the `MUXR_SESSION` / `MUXR_CONTROL_SOCKET` that `Application#pane_env` gave it at spawn, because a running process's environment can't be rewritten from outside. After a move they name the session the pane came from, which is why `bin/muxr-mcp` verifies `MUXR_PANE` against the session those vars name and re-resolves by pane id when it doesn't match — the pane id survives the move (`PaneTransfer` reuses it), the env doesn't.

- **`Terminal#dump_ansi` is the mirror's seed and the contract is a round-trip:** feeding its bytes to a blank emulator of the same size must reproduce the grid exactly (see `test_terminal_snapshot.rb`). It walks the *live* buffer, not `visible_cell`, so a scrolled-back owner still snapshots what the program thinks is on screen; it skips continuation cells (a wide lead already spans both columns) and emits `\e[2J` up front so blank tails cost nothing. `Terminal.sgr` was hoisted out of `Renderer#sgr` so a snapshot and an incremental frame describe a cell identically. It also emits `dump_modes` — the **scroll region is the load-bearing one**: a full-screen program sets DECSTBM once and then relies on bare index/reverse-index, so a copy that missed it scrolls the whole display instead of the band. DECSTBM homes the cursor, hence modes before the final cursor position. `#dump_transfer` / `#restore_transfer!` extend this with scrollback for the move path (a hole in history is exactly what `#resize` goes out of its way to avoid); history rows replay through a throwaway one-row emulator rather than duplicating the parser.

- **`LayoutManager` is pure** — `compute(layout, count, area, focused_index:, master_index:)` is the only entry point. Adding a new layout means adding a method here and an entry to `LAYOUTS`. No bookkeeping elsewhere; the Renderer calls `compute` on every render tick.

- **`:auto` is a resolver, not a geometry method.** `LayoutManager.resolve(layout, area)` maps `:auto` to `:spiral` when the content area is at least `AUTO_SPIRAL_MIN_COLS`×`AUTO_SPIRAL_MIN_ROWS` (180×30) and to `:stack` otherwise; every other layout passes through untouched. `compute` resolves before it dispatches, so nothing downstream ever sees `:auto`. It needs no size-change plumbing of its own: SIGWINCH → `RESIZE` frame → `Application#apply_size` updates `session.width/height`, and the next render tick re-resolves against the new area — the same path that already re-tiles every other layout. `Renderer#compose_panes` resolves once per frame (the resolved symbol, not `win.layout`, is what the monocle special-case tests) and the status bar shows the verdict as `layout:auto:stack` via `#layout_label`. Any future consumer that branches on `win.layout` must resolve first.

- **Drawer PTY is never torn down on hide.** `toggle/show/hide` only flip `@visible`; the shell process keeps running so its scrollback survives. Only `drawer reset` actually kills the PTY. The drawer (like every new pane) starts in the **session origin cwd** — the directory `bin/muxr` was launched from, captured once in `Application#initialize` (`@origin_cwd`).

- **`InputHandler` state machine:** `:idle` → (Ctrl-a) → `:prefix` → dispatches single key → `:idle`, OR `:prefix` + `:` → `:command` (buffered until Enter). `:confirm_quit` is a one-shot state entered by `:quit` / `Ctrl-a q`; it consumes one key and either calls `confirm_quit` (on `y`/`Y`) or `cancel_quit` (anything else). `:help` is the same shape — one-shot, cleared on any key. `Ctrl-a Ctrl-a` sends a literal Ctrl-a byte through to the focused pane.

- **`Window#promote_to_master`** does NOT just swap indices — it moves the focused pane to position 0 in `@panes` and resets both indices to 0. This keeps tall/grid layouts visually stable (master is always `panes[0]`).

- **`PTYProcess#cwd`** uses `/proc/<pid>/cwd` on Linux and falls back to `lsof -a -p PID -d cwd` on macOS/BSD. The lsof path is **synchronous and slow** (~100–300ms on macOS) — it runs on the event-loop thread when saving a session. Don't add new callers without thinking about it. (New panes no longer call it — they start in the session origin cwd, not the focused pane's.)

- **`ForegroundCommand.lookup(pid)`** is the moral cousin of `PTYProcess#cwd`: Linux reads `/proc/<pid>/stat` cheaply; macOS shells out to `ps -o tpgid=,pgid= -p <pid>` (and another `ps -o comm= -p <tpgid>`). Each macOS call is ~10–20ms × every pane × 750ms tick. It runs on `@foreground_poller` so the event loop is unaffected, but don't move it back to the main thread.

## Testing patterns

- PTY-spawning code paths are **dependency-injected**: `Pane.new` accepts `process:`, `Drawer.new` accepts `pane:`. Unit tests pass fakes (see `test_drawer.rb`, `test_session.rb`, `test_window.rb`) and never spawn a real shell.
- `test_helper.rb` deliberately loads only the pure pieces (`layout_manager`, `window`, `drawer`, `terminal`, `session`). Tests that need the full stack should `require "muxr"` themselves.
- `test_session.rb` swaps `Session::SESSIONS_DIR` in/out via `remove_const`/`const_set` around an `mktmpdir` block — copy this pattern if you add tests that touch the filesystem.

## Session file format

`~/.muxr/sessions/<name>.json` — only structural state is persisted (layout, indices, per-pane cwd, drawer visibility/cwd). Shell scrollback, command history, and process state are **not** restored; on restore, fresh shells are spawned with the saved cwds.

Note: the JSON file is now mainly a *cold-storage* fallback — between detaches the live session lives inside the running server process, so reattaching after `Ctrl-a d` gives you back the exact same shells with their full history. The JSON only matters if the server is killed (`Ctrl-a q`, machine reboot, etc.) and you want to spawn fresh shells in the saved layout next time. Run `:save` from inside muxr to write it.

## On-disk layout

```
~/.muxr/
 ├─ sessions/<name>.json   structural snapshot (manual `:save`)
 ├─ sockets/<name>.sock    server's Unix listener (created on server start, removed on shutdown)
 └─ logs/<name>.log        server stderr/stdout (appended on each spawn)
```
